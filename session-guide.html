    Why APIs, and the shop we'll build

    Everyone leaves knowing what we will have running by the end and why each layer exists.

    Say

    An API is a contract: "send me this, I promise to answer with that." The caller doesn't care what language or database sits behind it.

    A web API puts that contract on HTTP, so anything that can make an HTTP request can use it: a browser, a phone, curl, or another service.

    Fundamentals

    What REST actually means

    REST is a style for designing HTTP APIs around resources. Get the nouns, verbs and status codes right and most design questions answer themselves.

    Say

    REST (Roy Fielding, 2000) is a set of constraints, not a library. Four of them matter day to day:

    Resources have URLs

    Everything is a noun with an address. /menu is the collection, /menu/2 is one item.

    A uniform interface

    You act on resources with the same few HTTP methods everywhere. No custom verbs in URLs.

    Representations

    You never touch the resource itself, you exchange a representation of it, usually JSON.

    Stateless

    Each request carries everything needed to serve it (including auth). Any server copy can answer it. Hold onto this one: it is what makes scaling on Kubernetes trivial.

    Nouns in the URL, verbs in the method

    Instead ofWriteWhy
    POST /createOrderPOST /ordersThe method already says "create".
    GET /getMenuItem?id=2GET /menu/2Identity goes in the path. Query params are for filtering.
    GET /menu/2/deleteDELETE /menu/2GET must never change data. Crawlers and caches will call it.
    GET /espressoDrinksGET /menu?category=espressoOne collection, filtered, not a URL per filter.
    GET /orderItemsFor/42GET /orders/42/itemsNesting shows ownership. Stop at two levels.

    The methods, and the two properties that matter

    Safe means it changes nothing on the server. Idempotent means sending it once or ten times leaves the server in the same state, so a client can retry it after a timeout without fear.

    POSTCreate a new resource; server picks the idnono201 Created + Location
    PUTReplace the whole resourcenoyes200 OK

    Status codes: who should fix it?

    The first digit tells the caller what to do next. 2xx: done. 4xx: your request is wrong, don't retry it unchanged. 5xx: we failed, try again later.

    2xx success

    200
    OK. GET, PUT, PATCH worked.
    201
    Created. POST /menu, with a Location header.
    204
    No Content. DELETE /menu/8. Empty body.

    4xx caller's fault

    401
    Unauthorized. No X-API-Key header. "Who are you?"
    403
    Forbidden. Wrong key. "I know who you are, and no."
    404
    Not Found. GET /menu/999.
    409
    Conflict. Duplicate name, or ordering a sold-out item.
    422
    Unprocessable. Body failed validation. FastAPI does this for free.

    5xx server's fault

    500
    Internal error. An unhandled exception. Never send it on purpose.
    502
    Bad Gateway. menu-service answered something order-service didn't expect.
    503
    Unavailable. menu-service unreachable, or a pod failing readiness.
    504
    Gateway Timeout. menu-service took longer than 2 s.
    Design

    Path, query or body?

    Every piece of data in a request has one right place. Each place answers a different question.

    One request, all four places

    This is a real Brew Bar call: preview a price change on the Flat White without saving it.

    PATCH /menu/2?dry_run=true HTTP/1.1
Host: localhost:8001
X-API-Key: barista-secret
Content-Type: application/json

{"price_cents": 400}
    Path

    Which resource?

    2 is the item you're acting on. Change it and you're talking about a different thing.

    required · identity
    Query

    How should I read or handle it?

    dry_run=true changes how the server processes the request, not which item or what data.

    optional · has a default
    Body

    What are you sending?

    {"price_cents": 400} is the new data. It can be large, nested and structured.

    the payload · POST, PUT, PATCH
    Header

    What's true about this request?

    Who is asking (API key, token), what format, which version. Not about the resource itself.

    credentials · metadata

    Three questions, in this order

    1. Does it say which resource I mean? Put it in the path: /menu/7, /orders/42/items. Path parts are required; a URL without them points at something else.
    2. Is it the data I'm creating or changing? Put it in the body: a new menu item, the fields of a PATCH, the contents of an order.
    3. Does it filter, sort, paginate, or switch an option, and could it be left out? Put it in the query: ?category=espresso&limit=10, ?dry_run=true.

    Anything secret, or about the request rather than the resource, goes in a header.

    Say

    The trap people fall into: "it's an id, so it goes in the path." An id goes in the path only when it addresses the thing you're acting on. In POST /orders the item_id is just data about the new order.

    Say

    Quick test for query vs path: if the URL still makes sense with the parameter removed, it's a query parameter. /menu without ?category= is still the menu. /menu/ without 7 is a different resource.

    How FastAPI decides where to look

    You don't annotate each argument with "path" or "query". FastAPI reads the function signature:

    PATCH /menu/{item_id}menu-service/app/main.py
    @app.patch("/menu/{item_id}", response_model=MenuItem)
def patch_item(
    item_id: int,                    # named in the path template → PATH
    body: MenuItemPatch,             # a Pydantic model           → BODY
    x_api_key: Annotated[str, Header()],  # explicit Header()     → HEADER
    dry_run: bool = False,           # plain type, not in path    → QUERY
):
    ...
    Parameter is…FastAPI reads it from
    Named in the route, {item_id}Path, always required
    A Pydantic modelBody (JSON)
    int, str, bool, enum, not in the routeQuery; required unless it has a default
    Wrapped in Header() or Cookie()That header or cookie

    The real patch_item gets item_id through the get_item_or_404 dependency and the key through require_barista, but the rules are the same. Validation errors even tell you which place they checked:

     -H 'Content-Type: application/json' -d '{"price_cents": 400}'
# 422 {"detail":[{"loc":["query","dry_run"],"msg":"Input should be a valid boolean", ...}]}

    Gotchas

    • There's no optional path parameter. If a value can be left out, it belongs in the query.
    • Don't send a body with GET. Many proxies and clients drop it. For a search too complex for a query string, use POST /orders/search with a body.
    • Keep the query string short. Browsers and servers cap URLs at roughly 2–8 KB. Big or nested data goes in a body.
    • Query values are always strings on the wire. ?dry_run=true arrives as text; FastAPI's type hint turns it into a bool for you.

    Building menu-service with FastAPI

    Write type hints, get validation, JSON serialization and interactive docs without extra code.

    Say

    FastAPI is a Python web framework built on two libraries: Starlette (the HTTP plumbing, async) and Pydantic (data validation from type hints). Uvicorn is the server process that runs it.

    Hello, world

    main.py
    from fastapi import FastAPI

app = FastAPI()

@app.get("/hello/{name}")
def hello(name: str, excited: bool = False):
    return {"message": f"Hello {name}" + ("!" if excited else ".")}

    • excited isn't in the path, so it's a query parameter. Its type hint means "maybe" is rejected before your code runs.
    • Return a dict, get JSON. Open /docs: the docs were generated from those same hints.

    Model the resource

    Separate what clients send from what the server returns. The server owns id and updated_at, so clients can't set them.

    modelsmain.py
    class Category(str, Enum):
    espresso = "espresso"
    brew = "brew"
    tea = "tea"
    pastry = "pastry"

class MenuItemIn(BaseModel):                     # request body
    name: str = Field(min_length=2, max_length=40)
    category: Category
    price_cents: int = Field(gt=0, le=2000)      # money as integer cents
    available: bool = True

class MenuItem(MenuItemIn):                      # response body
    id: int
    updated_at: datetime

    Read a collection, with filters and pagination

    Optional query params with defaults. Query(le=50) caps page size so nobody asks for a million rows.

    GET /menumain.py
    @app.get("/menu", response_model=Page, tags=["menu"])
def list_items(
    category: Category | None = None,
    available: bool | None = None,
    max_price_cents: Annotated[int | None, Query(gt=0)] = None,
    limit: Annotated[int, Query(ge=1, le=50)] = 10,
    offset: Annotated[int, Query(ge=0)] = 0,
):
    items = list(DB.values())
    if category is not None:
        items = [i for i in items if i.category == category]
    if max_price_cents is not None:
        items = [i for i in items if i.price_cents <= max_price_cents]
    return Page(items=items[offset : offset + limit], total=len(items),
                limit=limit, offset=offset)

    Read one, with a reusable 404

    A dependency is a function FastAPI calls before your handler. Write the lookup once; GET, PUT, PATCH and DELETE all reuse it.

    dependencymain.py
    def get_item_or_404(item_id: Annotated[int, Path(ge=1)]) -> MenuItem:
    item = DB.get(item_id)
    if item is None:
        raise HTTPException(404, detail=f"Menu item {item_id} not found")
    return item

@app.get("/menu/{item_id}", response_model=MenuItem)
def get_item(item: Annotated[MenuItem, Depends(get_item_or_404)]):
    return item

    Create: 201, Location, and 409

    POST isn't idempotent, so a retried request could create duplicates. We guard on name and answer 409 Conflict.

    POST /menumain.py
    @app.post("/menu", response_model=MenuItem, status_code=201,
          dependencies=[Depends(require_barista)])
def create_item(body: MenuItemIn, response: Response):
    if any(i.name.lower() == body.name.lower() for i in DB.values()):
        raise HTTPException(409, detail=f"'{body.name}' is already on the menu")
    item = MenuItem(id=next_id(), updated_at=now(), **body.model_dump())
    DB[item.id] = item
    response.headers["Location"] = f"/menu/{item.id}"
    return item

    Update: PUT replaces, PATCH merges

    PUT takes the full MenuItemIn. PATCH takes a model where every field is optional; exclude_unset=True tells "not sent" apart from "sent as null".

    PATCH /menu/{id}main.py
    class MenuItemPatch(BaseModel):
    name: str | None = Field(default=None, min_length=2, max_length=40)
    category: Category | None = None
    price_cents: int | None = Field(default=None, gt=0, le=2000)
    available: bool | None = None

@app.patch("/menu/{item_id}", response_model=MenuItem,
           dependencies=[Depends(require_barista)])
def patch_item(body: MenuItemPatch,
               item: Annotated[MenuItem, Depends(get_item_or_404)]):
    changes = body.model_dump(exclude_unset=True)   # {"available": False}
    updated = item.model_copy(update={**changes, "updated_at": now()})
    DB[item.id] = updated
    return updated

    Guard writes with a dependency

    Same dependency mechanism, now for auth. Declaring it with APIKeyHeader also adds an Authorize button to /docs.

    authmain.py
    api_key_header = APIKeyHeader(name="X-API-Key", auto_error=False)

def require_barista(key: Annotated[str | None, Depends(api_key_header)]):
    if key is None:
        raise HTTPException(401, detail="Missing X-API-Key header")
    if key != API_KEY:               # read from env → a k8s Secret later
        raise HTTPException(403, detail="Wrong API key")

    Integrate

    How services find and call each other

    order-service never knows a pod IP. It knows a name, and Kubernetes DNS plus the Service do the rest.

    1. kubectl port-forward svc/order-service 8002:80 tunnels your request into an order pod.
    2. The order pod's httpx client resolves menu-service. CoreDNS answers with the Service's stable virtual IP.
    3. The request goes to that IP on port 80. Pods never change it, even as pods come and go.
    4. kube-proxy forwards to one ready menu pod on port 8000. The response's X-Served-By header names which one; order-service saves it as priced_by_pod.

    Never pass a downstream 404 straight through. To the customer, "menu item not found" and "your order was not found" are very different problems.

    Recap and questions

    • REST: resources in URLs, verbs in methods, meaning in status codes. Safe and idempotent decide what a client may retry.
    • Where data goes: path says which resource, body carries what you send, query tunes how you read it, headers say who's asking.
    • FastAPI: type hints give you validation (422), serialization and /docs. Dependencies reuse lookups and auth.
    • Containers: one immutable image, configured by environment variables, listening on 0.0.0.0.
    • Kubernetes: Deployments keep pods alive, Services give them a stable name, probes decide restart versus reroute.
    • Service to service: call by DNS name, inject the URL via ConfigMap, set timeouts, map every downstream failure to an honest status.
    • Stateless pods are what make all of the above work. State lives in a database.
